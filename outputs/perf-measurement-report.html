一、为什么需要实测

上一轮的性能改造交付时，收益来自静态代码推算——「增量渲染理论上只重建变化的节点」。这类结论有两个问题：一是无法量化，二是无法证伪。本次通过双轨测量把结论变成可复现的数字：

测量轨道方式作用
Node 侧 A/B 基准 可复现vm 隔离加载整份 agents.js + DOM 替身，驱动同一段合成事件流逐项计数：重建次数、缓存命中、遍历量
Electron 侧实测 真实渲染PERF=1 钩子在真实 Chromium 渲染进程驱动同一脚本帧间隔、长任务阻塞、真实 DOM 规模

两条轨道共用同一份 __perfDrive 驱动脚本与同一份事件流，保证口径一致；对照组取自 GitHub 远端 35700ef（改造前）的 renderer/agents.js。

五、测量方法与可信度

Node 侧 DOM 替身

本机无 jsdom / linkedom，故自建极简 DOM 替身（.perf/dom-harness.js），支持源码实际用到的全部 API：classList、innerHTML 解析、querySelector(All) 单类名与后代组合、replaceChild / appendChild / remove、isConnected。两版源码经 vm.runInContext 隔离加载，走完整原始代码路径而非抽取的纯函数。

埋点方式

用正则改写源码插入计数器（.perf/instrument.js）。正则改写存在静默失配风险，因此每轮都跑 probe.js 校验 9 个埋点是否全部命中——两版均 HIT 才继续。计数器声明用 var 而非 const，因为 vm 上下文中顶层 const 不挂到 context 对象。

已知的测量局限（如实说明）：
  • Node 侧 DOM 替身不实现真实布局与样式计算，因此耗时数字是相对比较有效，绝对值不可与浏览器性能工具直接对照；结论应以「改造前/后比值」为准。
  • Electron 侧为单次采样，未做多轮取中位数。跨会话的绝对帧率会受机器负载影响，但量级差异（4.8s vs 0.24s 长任务）远超噪声范围。
  • lineDiff 记忆化缓存在本基准中命中率为 0——因为合成的 change 事件内容各不相同，而缓存容量上限为 24 条，必然颠簸。该优化的收益需在「反复重绘同一批变更卡」的真实场景下才体现，本次基准未覆盖。
  • 沙箱禁止 Node spawn 子进程（EBUSY），Electron 对照组只能用 prepare-ab.js 分步装载 + 手动连跑两次完成。

六、复现方式

# Node 侧 A/B 基准（可复现，无需 GUI） node .perf/bench.js 100 3 # 100 entry × 3 轮 node .perf/bench-scenarios.js # B1/B2/B3 三场景 # Electron 渲染层 A/B（沙箱内需分步执行） node .perf/make-baseline-hook.js # 生成带钩子的对照组 node .perf/prepare-ab.js before # 装载改造前版本 PERF=1 PERF_ENTRIES=120 ./node_modules/electron/dist/electron.exe . node .perf/prepare-ab.js collect before node .perf/prepare-ab.js after # 还原改造后版本 PERF=1 PERF_ENTRIES=120 ./node_modules/electron/dist/electron.exe . node .perf/prepare-ab.js collect after # 输出对比表

七、结论

静态推算的核心判断——「增量渲染把长会话的重复 DOM 重建消除掉」——被实测证实，且幅度比推算更显著：

  • DOM 重建次数从与「事件数 × 累积条目数」的乘积级增长（10474），降到与「事件数」同阶（171）；
  • 用户可感知层面：4.8 秒界面冻结 → 236 毫秒；最长卡顿帧 125ms → 67ms；
  • 随会话增长收益扩大（60 entry 时 96.7%，100 entry 时 98.0%）。

同时，本次测量也纠正了一处方法论错误：首轮的「掉帧不降反升」结论源于不可比的采样窗口，若直接采信会得出错误判断。性能结论必须先验证测量方法本身的有效性。
